**Incident note (2026-07-30):** an earlier, looser draft of the UI check (`scratch/ui_check_product_delete_modal.mjs`, since rewritten) scoped its row/button locators by page-wide text matching (e.g. `page.locator('button:has-text("Cancel")').last()`) instead of a stable per-row identifier. Somewhere in that run, two **real** seed products (`Hamada Botox`, `k`) ended up soft-deleted as a side effect — not the throwaway test product the script intended to touch. This was caught immediately by manually diffing the catalog against the prior screenshot, confirmed via direct DB query (both rows had `deleted_at` set, not physically removed — DEC-038's soft-delete-by-default is exactly why this was recoverable), and fixed by clearing `deleted_at` back to `null` on both rows in `inventory_products` and the `page_settings` fallback. Restoration verified by re-reading both the DB and the live catalog UI, back to the original 3-product state. Root cause was the **test script's** locator strategy, not the application code. The rewritten script adds `data-testid` attributes to every delete-related button and the modal itself (also a minor accessibility win — the modal now has `role="dialog"`/`aria-modal`), plus an explicit baseline-safety assertion after every single step, specifically so this class of mistake fails loudly instead of silently mutating real data again.

## Per-check list

- [x] **Non-superadmin soft-delete:** as an `admin`-role (or any non-superadmin) staff user, delete a product from the catalog. Confirm it disappears from `GET /api/inventory/products`, but the row still exists in `inventory_products` with `deleted_at` set (not physically removed).
- [x] **Non-superadmin cannot hard-delete:** call `DELETE /api/inventory/products?id=X&hard=true` as a non-superadmin. Confirm `403 Forbidden`, and confirm the product was **not** deleted (soft or hard) as a side effect of the rejected request.
- [x] **Superadmin hard-delete (no history):** as `superadmin`, hard-delete a product that has no `consumption_entries`/`stock_movements`/`product_sales`/`purchase_lines` rows. Confirm `200` with `mode: "hard"` and the row is fully gone from `inventory_products` (query directly, not just via the filtered `GET`).
- [x] **Superadmin hard-delete blocked by FK (any of the four RESTRICT tables):** as `superadmin`, attempt to hard-delete a product that has `consumption_entries` **or** `purchase_lines` rows (both confirmed live). Confirm a `409` with a clear, actionable error message — not a silent `{ success: true }` while the row is actually still there (this was the original bug: "I can't delete the product").
- [x] **UI: non-superadmin sees exactly one delete button:** log in as a non-superadmin, confirm only a single trash-icon button appears per row, and clicking it opens the "Delete this product?" modal (soft-only) — never the permanent-delete modal or a raw `window.confirm`.
- [x] **UI: superadmin sees two distinct buttons:** log in as a superadmin, confirm each product row shows **two** separate action buttons — an amber "Soft Delete" (Archive icon) and a red "Permanently Delete" (Trash2 icon) — each opening its own matching in-page modal, not a browser `confirm()`.
- [x] **UI: no native dialogs, ever, including on error:** verified via `scratch/ui_check_product_delete_error.mjs` against a dedicated throwaway product seeded with real `purchase_lines` history (created directly in the DB, never touching real seed data). Attempting a superadmin hard delete on it renders the 409 message inline inside the same modal (red banner, `productDeleteError` state) instead of `alert()`, and the modal stays open so the user can Cancel or retry. Zero native dialogs fired at any point. Screenshot: `screenshots_2026-07-29/product-delete-error-inline.png`.
- [ ] **Restore is out of scope:** confirm (by reading DEC-038, not testing) that there is currently no UI to un-delete a soft-deleted product — this is a known, accepted gap, not a bug to chase in this checklist.
- [x] **Stock Valuation stat excludes soft-deleted products:** on the Inventory tab, note the Stock Valuation figure, soft-delete a product with real stock/cost, confirm the figure drops by exactly that product's `stock_quantity × purchase_price`, and returns to the original value once cleaned up. Verified via `scratch/test_product_delete_rule.ts`'s sibling check — this stat is a client-side reduce over the same `GET /api/inventory/products` list the delete rule already filters, so it inherited the fix automatically.
- [x] **A soft-deleted product cannot be sold:** `POST /api/inventory/products/sales` with a soft-deleted `product_id` returns `410` and does not write a `product_sales`/`invoice_lines` row or touch `stock_quantity`. This was the real Finance-integrity gap — without it, "deleting" a product wouldn't stop it from generating real revenue.
- [x] **A soft-deleted product cannot be restocked/purchased:** `POST /api/purchases` with a soft-deleted `productId` in any line returns `410` before any `purchases`/`purchase_lines`/`stock_movements` rows are written, and `restockInventoryProduct` itself also refuses to mutate a soft-deleted row (defense in depth for any other caller).
- [x] **`deductInventoryStock`/`restockInventoryProduct` freeze a soft-deleted product's stock:** both helpers now no-op (with a console warning) if the target row has `deleted_at` set, so its `stock_quantity`/`purchase_price` can't silently change through any internal code path, not just the two HTTP endpoints above.
- [ ] **Known residual gap (documented, not fixed here):** a soft-deleted product can still be referenced by a service's `service_consumables` recipe with no warning, and `applyCheckoutCosting`/consumption-entry writes at checkout don't check `deleted_at` either — a service whose recipe already includes a since-deleted product will keep costing/consuming it silently. Lower priority than sell/purchase since it doesn't let staff pick a deleted product from scratch, only continues an existing recipe reference; revisit if this surfaces in practice.
